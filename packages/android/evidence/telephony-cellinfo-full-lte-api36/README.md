# LTE, Android API 36

On a new `lte-parity` AVD (`emulator-5590`), `emu network speed lte` alone still yielded `CellInfoNr`. In Android Settings → mobile network → Preferred network type, selected **LTE** instead of **5G (recommended)**. The data-network property in `guest.txt` still read `NR_SA`; neither it nor the preference is the cell comparison. `registry.txt` is the earlier registry cache (NR); `registry-after.txt` is a later independent snapshot of the registered LTE identity. Its signal has changed since the API calls. Neither snapshot supplies any field to the pairing.

Both apps received precise location via Android Settings → Permissions → Location → Allow only while using the app. The `grant-*` files show both fine and coarse grants, with background location denied or not requested. System location was enabled. With Termux in the foreground, ran the fixed `termux-telephony-cellinfo` script (termux-api-package `9e7f1531e1aa4a9c1e261a2dbde4de93653c366e`) as `com.termux` against the installed v0.53.0 plugin. Then ran `am instrument -w -e scenario cellinfo-full-lte ai.opencode.android.test/ai.opencode.android.KeySmoke`; the scenario declines a full request, accepts the default summary, and accepts a new full request. `cellinfo-full-lte.out` includes the MCP payload and separate app-UID framework reads before/after; `mcp-full.json` extracts only the MCP response.

`comparison.json` joins the two API results on their unmodified `(type, mcc, mnc, ci)` values, checks uniqueness and full key sets, and compares JSON types and values (including array elements). The sole observed pair matched; absent optional measurements are listed separately and are not counted among the 12 fields. No fabricated cell objects or real phone were used.
